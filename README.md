# 로컬 5G 망 구축 — 해커를 위한 이동통신 실무서

> 초안 v0.1 · 2026-10-14 · 상태: **Part I 작성 중**

## 이 책이 존재하는 이유

**이동통신 기술이 특정 엔지니어의 전유물이어서는 안 된다.**

이 책은 진리를 탐구하는 호기심 많은 해커 성향의 공학도가, 로컬 5G 망(또는 4G 망)을 **스스로 구축해 보면서** 이동통신 전문가로 거듭날 수 있도록 안내하는 하우투 기술문서이자 안내서이자 바이블이 되고자 한다. 읽고 나면 통신사가 높은 연봉으로 데려갈 만한 인재가 되어야 하고, 현업 연구자가 펼쳐 놓고 공부할 만큼 깊어야 한다.

그래서 이 책의 원칙은 하나다. **독자 옆에는 물어볼 사람이 없다.** 전문가만 아는 용어, 전문가만 겪어 본 경험, 전문가만 가진 문서를 전제하지 않는다. 모든 용어는 처음 나온 자리에서 풀고, 모든 절차는 "왜 그렇게 설계됐는가"부터 설명한다.

이 책은 TCP/IP와 네트워크를 아는 소프트웨어 엔지니어가, 전자공학 전공 없이도 **사설 5G 망을 처음부터 직접 세우고 원리를 설명할 수 있게** 되는 것을 목표로 한다.

## 이 책을 읽는 사람

- 바이너리 리버싱, 패킷 분석, 방화벽 운용은 익숙하다.
- 프로토콜 헤더를 보면 필드가 무슨 뜻인지 바로 안다.
- 하지만 **안테나, 주파수, 샘플, 변조** 같은 전자 쪽 말은 "들어는 봤다" 수준이다.
- 오실로스코프는 써본 적이 없고, 트랜지스터는 "스위치 비슷한 것"이라고 알고 있다.

이 책은 그 수준에서 출발한다. 전문 용어가 나오면 **처음 나오는 자리에서 굵게 쓰고, 바로 뒤에 일상 비유와 정의를 함께 준다.** 정의를 건너뛰는 문장은 쓰지 않는다.

## 집필 기준: 쉽게, 그러나 결코 유치하지 않게

- **내용의 높이**는 현업 연구자가 읽어도 새로 배우는 것이 있어야 한다. 수식, 바이트, 표준 절 번호, 실측값을 뺀 "느낌 설명"은 쓰지 않는다.
- **설명의 높이**는 전자공학을 모르는 사람이 처음 읽고 따라올 수 있어야 한다. 용어가 나오면 그 자리에서 풀고, 비유를 한 번 주고, 바로 정확한 정의로 되돌아온다. 비유에서 끝내면 유치해진다.
- **용어의 독점을 깬다.** 휴대폰 엔지니어 모드 화면, 기지국 로그, 모뎀 응답에 뜨는 모든 약어는 이 책 어딘가에서 "무엇·단위·좋은 값·왜 중요한가·어디서 오는가"가 설명되어 있어야 한다. 부록 A 용어집이 그 색인이다.
- 쉬움의 기준은 "독자가 그 용어를 **남에게 다시 설명할 수 있는가**"다. 그게 안 되면 아직 안 쓴 것이다.

### 가르치는 방법: C++ 개발자에게 자바를 가르치듯

독자는 머리가 비상한 사람이 아니라 **갈아 넣어서** 실력을 올린 사람이다. 그 방식은 전자 쪽에서 통하지 않는다 — 실험 한 번이 반나절이기 때문이다. 그래서 이 책은 독자가 **이미 가진 지식에 새 이름을 붙이는 것**으로 대부분을 끝내고, 대응물이 없는 개념에만 깊이를 쏟는다. 용어 수준은 전자공학도가 아니라 **평범한 리눅스/윈도우 애플리케이션 개발자**에 맞춘다.

**이미 아는 것 → 이동통신의 이름** (책 전체의 뼈대. 각 장은 이 표의 자기 줄에서 시작한다)

| 독자가 아는 것 | 이동통신에서의 이름 | 장 |
|---|---|---|
| 사운드카드 ADC/DAC, 샘플레이트 | SDR, I/Q 샘플 | 02 |
| FFT | OFDM (IFFT 한 번이 송신) | 03 |
| 시분할·주파수분할 스케줄러 | 슬롯 × 부반송파 격자, PRB | 03 |
| 와이파이 SSID 비콘 | SSB (PSS/SSS/PBCH) | 03 |
| 802.11 채널 번호 | ARFCN | 03 |
| 스마트카드/HSM/TPM | SIM, Ki 가 안 나오는 설계 | 04a |
| ISO 7816 APDU (이미 UART 해킹하며 봤을 것) | 카드와의 대화 | 04a |
| RADIUS + LDAP | AMF+AUSF+UDM+UDR | 04, 05 |
| DHCP 서버 + NAT 라우터 | SMF + UPF | 04, 07 |
| QoS 정책 서버 | PCF, PCC 규칙 | 07 |
| Consul / k8s 서비스 디스커버리 | NRF | 05 |
| API 게이트웨이 / 사이드카 | SCP | 05 |
| REST + HTTP/2 + OpenAPI | SBI | 05 |
| 챌린지-응답, HMAC | AKA, MAC-A, RES | 06 |
| TLS 마스터 시크릿 → 세션 키 파생 | CK/IK → K_AMF → K_gNB 키 계층 | 06 |
| 공개키로 ID 암호화 | SUCI | 06 |
| VXLAN / GRE | GTP-U, TEID | 07 |
| OpenFlow match/action/meter/counter | PFCP PDR/FAR/QER/URR | 07 |
| TUN 장치 (OpenVPN) | UPF ogstun | 07 |
| SIP/RTP (VoIP 를 안다면), outbound proxy, registrar | P-CSCF, S-CSCF, IMS 등록 | 08 |
| DNS SRV/NAPTR | IMS 도메인 해석, I-CSCF 찾기 | 08 |
| 시리얼 콘솔, UART, minicom | AT 명령 포트 | 11a |
| 다이얼업 PPP (써 봤다면) | PDU 세션의 조상 | 11b |
| REST 의 OPTIONS/GET/PUT/POST | AT 의 `=?`/`?`/`=`/실행 | 11c |
| TLV, protobuf, gRPC | QMI, Diameter AVP | 11d |
| 라우터 콘솔 포트 = 라우터 소유 | 모뎀 제어 포트 = 권한 채널 | 11e |
| `iwconfig`/`iw` 의 signal, bitrate | RSRP/RSRQ/SINR, MCS | 11f |

**비유의 높이**: 독자는 프로토콜을 **패킷을 열어 읽는 사람**으로 안다. 구현하는 사람으로는 모른다. TLS 면 ClientHello 의 SNI 가 평문이고 어느 버전이 깨지는지는 알지만, 키 유도의 단계 구조는 모른다. 그러므로 비유는 **독자가 와이어샤크에서 본 것**에만 댄다. "TLS 의 HKDF 처럼" 은 금지, "ClientHello 의 SNI 가 평문이라 어느 사이트 가는지 보이는 것처럼" 은 허용. 비유를 쓰고 나서 그 비유 자체를 한 문장으로 설명해야 하면 그 비유는 틀린 것이다.

**대응물이 없는 것** — 여기에 깊이와 분량을 쏟는다: 전파의 거리 감쇠와 dB(01), 샘플과 I/Q 가 복소수인 이유(02), 시간·주파수 격자와 TDD 보호 시간(03), 키가 카드 밖으로 안 나오는 설계와 ADM 의 비복구(04a), 움직이는 단말을 찾는 TAC·페이징·RRC 상태(04, 11f), 상향 슬롯이 하향 TCP 를 묶는 TDD 의 성질(07), 전파 품질이 매 밀리초 변해서 생기는 CQI/MCS/HARQ 루프(11f).

### 독자의 실험 도구: 파이썬과 와이어샤크

전자공학도는 오실로스코프를 들지만 이 독자는 **파이썬**(라이브러리로 조작)과 **와이어샤크**(패킷을 읽는다)를 든다. 이 책의 모든 "직접 해보기"는 그 둘로 한다. 다행히 와이어샤크는 이 책에 나오는 프로토콜을 **전부 기본 디섹터로 해석한다.**

| 구간 | 와이어샤크 표시 필터 | 무엇이 보이나 |
|---|---|---|
| 기지국 ↔ AMF (N2) | `ngap` / `nas-5gs` | 등록 요청, 인증, 보안 모드, 세션 수락 — NAS 가 암호화되기 전까지는 필드까지 |
| 기지국 ↔ UPF (N3) | `gtp` 또는 `udp.port == 2152` | 터널 헤더와 그 안의 단말 IP 패킷(평문) |
| SMF ↔ UPF (N4) | `pfcp` | PDR/FAR/QER 규칙 설치 |
| 코어 조각끼리 (SBI) | `http2` | REST 경로와 JSON 본문 |
| IMS ↔ HSS | `diameter` | UAR/MAR/SAR/LIR 과 AVP |
| IMS 시그널링 | `sip` / `sip.Method == "INVITE"` | 홉마다 쌓이는 Via, Record-Route, SDP |
| 음성 미디어 | `rtp` → 전화 → RTP 스트림 분석 | 패킷 수, 손실, 지터 |
| 모뎀 제어 | (와이어샤크 아님) `--apdu-trace`, `pyserial` 로그 | AT 바이트, APDU 바이트 |

캡처 위치는 호스트의 도커 브리지 `br-b33ecd87724d` 다. 모든 컨테이너 간 트래픽이 거기를 지난다. `tcpdump -i br-b33ecd87724d -w cap.pcap` 로 받아 와이어샤크로 열면 위 필터가 전부 먹는다. 파이썬 쪽은 `pyserial`(AT), `pyscard`/`pySim`(APDU), `scapy` 또는 `pyshark`(패킷)를 쓴다.

### 목소리: Project Zero 블로그처럼

이 책은 **해커의 눈과 문화**로 쓴다. 참고 모델은 Google Project Zero 의 블로그 글이다. 그 글들의 공통점은 이렇다.

- **1인칭 조사 서사.** "우리는 이걸 켰고, 이게 보였고, 이상했고, 소스를 열었고, 여기였다." 결론을 먼저 던지고 근거를 붙이는 교과서 순서가 아니라, **관찰 → 가설 → 확인 → 다음 가설**의 순서로 쓴다. 독자는 조사를 따라가면서 시스템을 배운다.
- **실제 산출물을 그대로 싣는다.** 로그 줄, 헥스 덤프, 캡처, 소스 발췌, 설정 파일. 요약하지 않고 원문을 보여 주고 그 옆에서 읽어 준다.
- **막다른 길을 지우지 않는다.** 틀린 가설, 헛수고한 반나절, 뒤집힌 결론을 그대로 둔다. 그것이 독자가 같은 함정을 피하는 유일한 방법이다.
- **소스까지 내려간다.** "500 이 났다"에서 멈추지 않고 그 문구가 Kamailio 설정의 어느 `failure_route` 블록에 있는지, PyHSS 의 어느 함수가 그 AVP 를 만드는지, srsRAN 의 어느 init 스크립트가 플레이스홀더를 치환하는지 **파일과 줄**로 짚는다.
- **건조하고 정확하다.** 감탄사도 과장도 없다. 틀렸으면 틀렸다고 쓴다.

그래서 이 책의 각 장은 "X 란 무엇인가"가 아니라 **"우리는 X 를 세우려 했고, 이런 일이 벌어졌다"** 로 시작한다. 원리는 그 서사 안에서 필요한 순간에 나온다.

### 이론서가 아니다

이 책은 **구축서**다. 모든 절은 "그래서 지금 네 장비에서 이것을 치고 이것이 보여야 한다"로 끝나야 한다. 원리 설명은 그 명령과 그 출력을 이해하기 위해서만 존재한다. 어느 절을 읽고 독자가 터미널에서 할 일이 떠오르지 않으면 그 절은 잘못 쓴 것이다.

- **유명한 것은 짧게.** TLS, HTTP/2, REST, DHCP, NAT, VXLAN, 서비스 디스커버리는 이름만 대고 지나간다. 독자가 아는 것을 설명하면 모욕이다.
- **패킷 해부도는 "누가 어디서"가 붙어야 완성.** 헤더 필드 표 뒤에는 반드시 "이 헤더를 어느 프로세스의 어느 부분이 만들고, 어느 프로세스가 벗기고, 그 사이 어느 커널 장치를 지나는가"를 **우리 배포의 컨테이너·프로세스 이름으로** 쓴다.
- **gNB(기지국) 장이 가장 길다.** 핵심 서비스다. 설정 파일 전 항목, 기동 로그 전 줄, 단말이 붙는 동안 기지국 안에서 일어나는 일, 바꿀 수 있는 것과 바꾸면 안 되는 것, 실패 양상 전부를 다룬다. 분량을 아끼지 않는다.

### 문체 기준 (교과서 문체 금지)

흔한 교과서는 이렇다: 문장은 짧고 단순한데 용어는 설명 없이 난립하고, 정작 내용은 뉴스만 봐도 아는 것을 어려운 말로 포장한다. **이 책은 그 반대다.**

- **본문은 이어지는 산문이다.** 표와 글머리표는 절 끝의 요약에만 쓴다. 본문에서 용어를 표 칸 안에 정의하지 않는다. 용어 하나에 문단 하나를 준다.
- **"왜"가 "무엇"보다 먼저 온다.** 설계가 그렇게 된 이유(문제 → 시도 → 해법)를 서사로 풀고, 그 끝에 이름을 붙인다. 이름부터 던지고 뜻을 뒤에 붙이지 않는다.
- **문장은 길어도 된다.** 인과를 한 문장에 담아야 하면 담는다. 짧게 끊어서 독자에게 연결을 떠넘기지 않는다.
- **내용은 깊고 말은 쉽다.** 수식·바이트·실측값을 빼지 않는다. 대신 그 수식이 무엇을 뜻하는지 일상어로 한 번 더 말한다.
- **독자가 이미 아는 것에서 출발한다.** TCP/IP, 리눅스, 바이너리, UART. 거기서 한 걸음씩 간다.
- 골격만 있는 장은 파일 머리에 `> 상태: 골격 초안 — 풀어쓰기 예정` 을 단다. 풀어쓴 장은 그 표시를 뗀다.

## 표기 규칙

- **굵은 글씨**: 그 장에서 처음 등장한 전문 용어. 옆에 정의가 붙는다.
- `코드`: 실제 명령이나 설정 값. 이 실험실에서 실제로 쓴 것이다.
- ⚠️: 실수하면 장비나 법규에 문제가 되는 지점.
- 🔎: 직접 확인해 볼 수 있는 방법.
- **측정**과 **추정**을 구분한다. 측정값은 이 실험실에서 실제로 잰 값이고, 추정값은 계산으로 얻은 상한이다. 둘을 섞지 않는다.

## 안전과 법규 (반드시 먼저 읽을 것)

이 책이 다루는 실험은 **전파를 실제로 방사하는 부분**을 포함한다.

- 이동통신 주파수는 나라마다 허가 대상이다. 허가 없이 공중에 송신하면 법을 어기는 것이다.
- 이 책의 실험은 **차폐함(전파가 밖으로 나가지 않도록 막힌 상자)** 안에서, 케이블로 직결하는 것을 전제로 한다.
- 공중 방사 시험은 해당 국가의 무선국 허가 절차를 거친 뒤에만 한다.
- 예시로 쓰는 PLMN 001/01 은 국제 표준이 시험용으로 정한 번호다. 상용 사업자의 번호와 주파수는 쓰지 않는다.

## 민감정보 원칙

책에는 다음을 **실제 값으로 넣지 않는다**: 가입자 인증 키(Ki, OPc), 관리자 PIN(ADM), 개인 식별 번호(PIN/PUK), 실험실 내부 주소, 실제 전화번호. 모든 예시는 `<KI>`, `<OPC>`, `<ADM1>`, `<MSISDN>` 같은 자리표시자로 쓴다.
